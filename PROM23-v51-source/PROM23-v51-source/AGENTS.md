- B2C;

- физических лиц;

- юридических лиц;
- снабженцев;

CONTENT PARITY  
+  
FUNCTIONAL PARITY  
+  
BUSINESS LOGIC PARITY

https://prom.myfast.space/

При этом mobile UX должен быть значительно лучше desktop/web UX.

# 3. ВАЖНОЕ ОГРАНИЧЕНИЕ

Доступа к текущему production Bitrix / production DB НЕТ.

Нельзя заявлять:

«проверил production Bitrix».

Нельзя строить задачу так, будто production backend доступен.

Используй:

- предоставленный source code;
- временный сайт;
- локально доступные конфиги;
- существующие handlers;
- существующие API contracts.

Если для реальной интеграции отсутствуют credentials или внешний runtime:

реализуй архитектуру и flow полностью,

но пометь:

`BLOCKED_BY_EXTERNAL_ACCESS`.

Никогда не заменяй отсутствующий внешний доступ fake success.

# 9. B2C / B2B

B2C и B2B — равнозначные части продукта.

Default:

B2C / «Для себя».

Должно существовать понятное переключение:

`Для себя`  
/  
`Для бизнеса`.

Переключение не должно быть декоративным.

Оно должно использовать существующую backend-модель там, где применимо:

- корзины;
- организации;
- цены;
- заказы;
- документы;
- checkout.

---

# 10. B2C

Существующие consumer-функции не должны пропасть.

Проверить и сохранить:

- заказы;
- избранное;
- сравнение;
- лист ожидания;
- отзывы;
- вопросы;
- обращения;
- возвраты;
- адреса;
- способы оплаты;
- уведомления;
- недавно просмотренные товары.

# 11. B2B

Сохранить:

- организации;
- активную организацию;
- организационные корзины;
- закупку;
- КП;
- документы;
- ЭДО;
- B2B-заказы;

- взаимодействие с менеджером;
- реальные корпоративные сценарии.

# 12. КОРЗИНА

После добавления товара пользователь должен попасть в корзину максимум за 1 tap.

Обязательно:

- global cart;
- cart badge;
- quantity;
- remove;
- discounts;
- coupon;
- total;
- checkout.

---

# 13. CHECKOUT

Нельзя упрощать checkout без анализа source code.

Обязательно проверить:

- физлицо / организация;
- все реальные способы доставки;
- все реальные способы оплаты;
- промокоды;
- итоговую сумму;
- регион;
- адрес;
- организацию;
- пересчёт.

Backend является authoritative source для totals.

---

# 14. PAYMENT

Если приложение рекламирует способ оплаты:

он должен быть реально доступен в checkout.

Особенно:

- карты;
- СБП;
- Yandex Pay;
- Split;
- счёт;
- банковский перевод;
- другие обнаруженные способы.

Если integration отсутствует или недоступна:

не обещать её пользователю как работающую.

# 15. DELIVERY

Все реальные варианты доставки сайта должны быть восстановлены.

Не заменять их одним абзацем:

«менеджер поможет».

В checkout пользователь должен выбирать доступный вариант.

# 16. LOCATION

Свободный текст нельзя считать выбранным населённым пунктом.

Для РФ использовать structured location identity:

FIAS / GAR.

Разделять:

- Settlement;
- ServiceRegion;
- Warehouse;
- DeliveryAddress.

Поддерживать не только города:

- сёла;
- станицы;
- посёлки;
- хутора;
- другие населённые пункты.

# 19. HOME

Главная должна быть commerce-first.

Текущие блоки, которые не следует сохранять в существующем виде:

- «Покупать проще, когда всё рядом»;
- «Что планируете делать?»;
- дублирующий «От выбора до получения».
