# Source CMS runtime adapter — Stage 9 (CMS)

`integrations/runtime/src/CmsContentDriver.php` is the PHP read adapter behind `integrations/runtime/cms-sync.php`, an **offline** sync job — not a per-request bridge. Content pages change rarely and the public `/api/v1/content/pages/:slug` BFF must not depend on live Bitrix uptime, so the driver runs on an isolated/staging Bitrix instance, writes a `site-pages.live.json` + manifest pair, and `server/integrations/public-content.mjs`'s new live overlay (see `docs/api/public-content.md`) picks it up per-slug.

Treat that capture as real but dated (a week-plus old relative to "today"), not as a live source of truth — re-run the sync before trusting it for anything time-sensitive. ### Static-only pages (`cookies`, `recommendations`, `privacy`)

`cookies`, `recommendations`, and `privacy` are all pure hardcoded PHP/HTML templates with **no** backing CMS element actually served to users — not a driver limitation, a real gap in the site's content model (the `IBLOCK_ID_PAGES`/`CODE=/privacy/` element is not this page's source; see the table entry above — it's dead/orphaned content). `fromStaticTemplate()` (the `static-template` adapter type) works around this by reading the template *file* directly off disk and extracting its `<h1>`/`<h2>`/`<h3>`/`<p>`/`<li>` body — it never executes the PHP, matching the existing snapshot pipeline's "never run site PHP/JS" rule (`integrations/README.md` #9). Its `provenance` is the file path + `filemtime()`, not an element ID/revision, since there is no element. All three are now confirmed and wired.

**Bug found and fixed 09.10.2026**: the block-extraction regex originally only matched `<h1|h2|h3|p>`, not `<li>`. `cookies`/`recommendations` both consistently wrap every bullet as `<li><p>…</p></li>`, so this never mattered for them — the inner `<p>` got matched directly either way. But `privacy-policy/index.php` has several `<ul>` blocks (e.g. lines~528-612) where bullets are raw text directly inside `<li>` with **no** `<p>` child at all — those were silently dropped, losing real legal-disclosure text with no error (the extractor still "succeeded", just incompletely). Added `li` to the regex alternation; a `<li>` encountered before any inner `<p>` is matched as one block (the lazy `.*?` extends to the matching `</li>`, so `<li><p>…</p></li>` still yields exactly one paragraph, not a double count — verified in the new `test/CmsContentDriver.test.php`, not run, no PHP CLI this session either).

This is a real workaround, not a substitute for a proper fix. Two options remain open with the content owner:

1. Migrate the text into new `IBLOCK_ID_PAGES` elements (recommended — makes them editable and puts them on the same footing as every other page, with a real revision/provenance instead of a file mtime), then switch each to a `page-element` entry.
2. Keep `static-template` permanently — acceptable for legal boilerplate that rarely changes, but every edit still means redeploying a template file and re-running the sync, and if the template's markup shape ever changes, the block-extraction regex silently stops finding content (fails closed via `CMS_TAB_EMPTY`, not silently wrong — but still needs a human to notice and fix the extraction).

## Adapter design (`CmsContentDriver.php`)

- `page-element`: base `IBLOCK_ID_PAGES=9` element selected by `CODE` (identical filter to the site's own `\Prom\Page::init()`, `local/class/Prom/Page.php`). Optional `textProperty` reads one plain UF_ text field directly (used for `personal-data`'s `UF_USER_AGREEMENT_TEXT`). Optional `banner` resolves the single-value `UF_BANNER_PAGE`-style link into `IBLOCK_ID_BANNER`'s own `TITLE`/`DESCRIPTION` properties as an intro section (`about`/`brands`/`suppliers`/`franchise` all use this). Optional `blocks[]` resolve the page element's own UF_ *list* properties (arrays of linked-element IDs) against their target iblock, in stored order, into one section per block — each block can set `asBullets` (list vs paragraph rendering), `nameOnly` (skip appending `PREVIEW_TEXT`, for iblocks that just repeat boilerplate text per card), `previewOnly` (the inverse — drop `NAME` instead, for `franchise`'s `cases-and-reviews` block: confirmed 09.10.2026 that `IBLOCK_ID_CASES_AND_REVIEWS`'s `NAME` is never requested as visible content by any of the 4 templates sharing it, only ever used as an `<img alt="">` — i.e. Bitrix's default per-element placeholder, not real editorial text), `yearField` (prefix each line with `FormatDate('Y', MakeTimeStamp(ACTIVE_FROM))`, for `awards`), or `titleProperty` (read the block's own heading from a page-element UF_ text property instead of a hardcoded label, for `suppliers`' achievements block).
- `delivery-tab`: the single `/delivery/` page element carries five tabs (`returns`/`details`/`offer`/`checkout`/`warranty`) as **parallel** multi-value UF properties — `UF_CONTENT_TABS` (label), `UF_CONTENT_TABS_TEXT` (body), `UF_CONTENT_TABS_SLUG` (URL slug), `UF_CONTENT_TABS_H1` (heading) — matched by index. The adapter resolves the tab by matching `tabSlug` against `UF_CONTENT_TABS_SLUG`, not by array position, so editors can reorder tabs without breaking this mapping. Long tabs (e.g. `oferta`'s 124 numbered clauses) are split across `id`/`id-2`/`id-3`... chunks of 100 paragraphs rather than raising the shared 120-paragraph safety cap just for this source.
- `faq-list`: `IBLOCK_ID_FAQ=10` elements listed directly (`ACTIVE=Y`, sorted), one section per Q&A item (`NAME`=question, `DETAIL_TEXT`/`PREVIEW_TEXT`=answer — answers live in `PREVIEW_TEXT` on this iblock, `DETAIL_TEXT` is unused/empty-string).
- `static-template`: reads a template *file* directly off disk (path confined under `siteRoot`, never executed) and regex-extracts its `<h1>`/`<h2>`/`<h3>`/`<p>`/`<li>` body between the first heading and the `bitrix/footer.php` include — the only type with no iblock element actually served behind it (`cookies`, `recommendations`, `privacy`). `<li>` is matched alongside the heading/paragraph tags specifically to catch bullet lists that put raw text directly inside `<li>` with no `<p>` child (found in `privacy-policy/index.php`) — see the 09.10.2026 bugfix note above.
- Every path goes through `validated()`, a PHP-side mirror of `public-content.mjs`'s `normalizeContentPage()`/`safeContentUrl()` checks (text length/control-char/`<>` rejection, section ID uniqueness and pattern, same-site HTTPS link allowlist excluding `/local`, `/bitrix`, `/personal`, `/organization`, `/api`, `*.php`). This is defense-in-depth, not a replacement for the Node-side check — its purpose is to let `cms-sync.php` fail loudly **per slug** with that slug's provenance in its error output, instead of a bad element only surfacing later as an unexplained drop on the BFF side.
- Every resolved page carries a `provenance` object: `source` (which iblock constant, or `STATIC_TEMPLATE`), `iblockId`/`elementId` (or `file`, for `static-template`), and `lastModified` (the source element's `TIMESTAMP_X`, or the template file's `filemtime()`). This is written into the live snapshot's per-page envelope (`server/integrations/public-content.mjs` — `provenance` field, additive to the existing `{schemaVersion,revision,sourceCheckedAt,mode,page}` shape, schema updated in `public-content.schema.json` to allow `mode:'live-cms'` alongside `'source-snapshot'`).

## Migration plan (no downtime)

1. **Audit before enabling.** `about`, `personal-data`, `brands`, `suppliers`/`cooperation`, `franchise`, `awards`, the five `/delivery/` tabs, `cookies`, `recommendations`, `privacy`, and now `promotions` are confirmed against source templates (or, for `promotions`, against the new owner-approved iblock) and wired in `cms-sync.config.example.php`. Only `faq` is still deliberately left unwired (owner decision needed on the curated snapshot's mismatched mapping — see table). Any slug not in that file yet still needs someone to read its own `index.php`/template and fill in its `blocks`/`textProperty`/`banner` before enabling — an unaudited `page-element` slug doesn't crash, it silently serves incomplete or wrong content, which is worse.
2. **Run `cms-sync.php` on an isolated Bitrix instance**, never against `prom23.ru` directly (same rule as `region-mapping/`). It writes `site-pages.live.json` + `site-pages.live.manifest.json`; a failure on one slug is recorded in the manifest's `errors` map and does not block the others.
3. **Deploy the two files** outside the web root, mode `0600`, next to the runtime's other private config.
4. **Point the BFF at them**: `createPublicContentService({ liveSnapshotPath: '/private/path/site-pages.live.json', liveSlugs: ['about'] })` — start with exactly one slug.
5. **Verify** that slug's response against the curated one (title/sections/links match expectations, ETag changes, ETag/304 still works) before adding the next slug to `liveSlugs`.
6. **Re-run the sync on a schedule** (cron) appropriate to how often content editors actually change these pages — this is not a real-time CMS, and does not need to be; each run's manifest `generatedAt` plus each page's `provenance.lastModified` gives enough staleness signal without polling Bitrix per request.
7. Curated `mobile/src/content/sitePages.ts` / `data/site-pages.json` stay as the fallback for every slug not yet in `liveSlugs` — `promotions` is now buildable and verified live (see above), but still needs its own `liveSlugs` rollout step like any other slug; `faq` stays fallback-only until the owner decision above lands.

## What this does not touch

`mobile/src/content/editorialContent.ts` and branch-specific presentation data are untouched — per `integrations/README.md` #9 they are a separate local layer, not managed by this CMS endpoint, and nothing in `CmsContentDriver.php` or `cms-sync.php` reads or writes them. No production content was changed this session; `CmsContentDriver` only calls `CIBlockElement::GetList`/`GetNextElement`/`GetProperty`, never `Add`/`Update`/`Delete`.
