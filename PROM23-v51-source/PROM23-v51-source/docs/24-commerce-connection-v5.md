# Подключение предложений оплаты и доставки

## Что реализовано в интерфейсе

Каталог, карточка товара, корзина и оформление используют одни компоненты PaymentBenefit/DeliveryBenefit. В карточке — сумма одного товара, в корзине — сумма всех позиций с количеством. Из компактной плашки открываются подробности внутри приложения. Для компании выводится оплата по счёту и ЭДО.

`mobile/src/api/commerce.ts::loadCommerceOffer` — граница подключения, сейчас возвращает null. Переданный AbortSignal нужно передать HTTP-клиенту. Не подменять этот метод созданием заказа или платежа: запрос предложения должен быть только расчётом.

Контракт CommerceRequest: контекст покупателя, выбранный город, productId, quantity, priceKopecks. Ответ CommerceOffer: requestKey, expiresAt, split.payments (сумма/подпись каждого платежа), split.terms, plus.points/terms, delivery (id/способ/имя/цена/период/адрес/подпись отслеживания). Ключ связывает ответ с текущим заказом и должен возвращаться сервером после проверки. Цены из клиента нельзя считать доверенными; Битрикс пересчитывает их и возвращает обновление каталога при расхождении.

`currentCommerceOffer` отбрасывает ответ для другого города, цены, количества или покупателя, истёкший ответ и некорректные суммы. `useCommerce` отменяет запрос при уходе/изменении параметров и убирает предложение по expiresAt. Для полного каталога нужны серверное объединение/кеширование предложений и ограничение запросов по видимости карточек.

## Исходники и провайдеры

- Вложенный сайт: `local/templates/main/components/bitrix/catalog.element/old/template.php`, `local/templates/main/components/bitrix/sale.order.ajax/main/template.php` — подключение Пэй и карточки.
- `local/php_interface/lib/delivery/ProductDeliveryCalculator.php` + Providers — габариты/вес из Bitrix ProductTable, город/склад, количество; токены только на сервере.
- `Providers/PickupProvider.php` — бесплатный самовывоз, период из настроек региона. Готовность к выдаче необходимо подтверждать фактическим заказом.
- https://prom.myfast.space/delivery/ — бесплатный довоз до терминала ТК; сама перевозка оплачивается отдельно.
- https://pay.yandex.ru/docs/ru/custom/mobile-sdk/yandex-pay-kit/ — актуальный нативный SDK.
- https://pay.yandex.ru/docs/ru/custom/web-sdk/badges — персонализация и товарный контекст бейджа.
- https://pay.yandex.ru/docs/ru/custom/web-sdk/ultimate-widget — график с учётом личного лимита, первый платёж может отличаться.

`prom-krd.ru` использует Яндекс-витрину (yastore-b2c), а исходный prom.myfast.space — Битрикс; публичные merchant ID у них разные. Числа из скриншотов не являются универсальным тарифом или процентом для будущего prom23.ru. Ни merchant, ни авторизацию другого магазина не переносили. SDK провайдера пока не установлен; произвольные внешние скрипты не добавлены в CSP.

## Поведение без интеграции

Пример Сплита = сумма товаров / 4 с точностью до копейки и сохранением суммы. Рядом видна подпись «пример», в подробностях — отличие от одобренного графика и исключение доставки из примера. Без подтверждённого предложения количество баллов не показывается, а объясняется способ получения через Пэй. Без расчёта перевозчика не показываются придуманные даты/цены: остаются способы получения, адрес/часы филиала, бесплатный самовывоз и обращение менеджеру. «Проверить срок и стоимость» показывает понятный результат недоступности.

## Перед запуском

Подключить безопасный HTTPS API Битрикса, сопоставить реальные идентификаторы SKU и регионов, проверить персональный Пэй/Сплит и подписку Плюс, вес/габариты/доступность ПВЗ для крупного оборудования, НДС/ЭДО B2B, отмену старых расчётов. Нативный Pay Kit и обработку возвращения из оплаты проверяют на устройствах. Реальные заказы, CRM, 1С и чеки этой итерацией не отправлялись.
