## Конкретный контракт согласий — следующий этап, не действующий endpoint

Текущий `SiteFormRequest.consents` содержит только name, accepted и documentIds (`mobile/src/api/site.ts:11`). Перед записью необходимо:

1. Получать от backend актуальный documentId/version/contentHash, purpose и channel с текстом, который реально показан пользователю. Клиент не назначает версию сам.
2. Разделять принятие условий, ознакомление с политикой и согласия по целям. Для push/email/SMS marketing хранить независимые решения; отказ не закрывает обычную покупку.
3. Записывать серверный eventId, subject binding, purpose/channel, documentVersion/contentHash, accepted/revoked, server UTC timestamp и acceptanceSource. Состав доказательств и сроки утверждаются в processing-register; IP/полный user-agent не добавлять автоматически «на всякий случай».
4. Повторный запрос с тем же idempotency key не создаёт второе согласие. Устаревшая версия возвращает отдельную ошибку и обновлённый документ; не соглашаться от имени пользователя.
5. Отзыв немедленно закрывает соответствующий sender gate и отменяет ещё не отправленные marketing jobs; он не имитируется только положением switch. Каналы сервисных уведомлений обрабатываются по отдельно утверждённой модели.

Source-документы содержат расхождения оператора/ОГРН, дат и доменов; они перечислены в [20-consent-source-audit.md](20-consent-source-audit.md). Не выпускать копии как юридически согласованную политику приложения и не исправлять реквизиты догадкой.

## Удаление и отзыв доступа: требуемый связанный процесс

`/forms/account-delete` — подготовленная форма. Нужен настоящий server workflow: повторное подтверждение identity → deletion request с номером/статусом → revoke всех refresh families и device tokens → прекращение необязательных отправок → очистка/анонимизация профиля, адресов, интересов и файлов по утверждённой карте → подтверждённые downstream jobs Bitrix/CRM/1С/подрядчиков → завершение и доказательства.

Обязательный архив заказов/учёта отделяется от активного аккаунта с ограниченным доступом и утверждённым сроком, а не скрыто сохраняется как доступный профиль. Сроки не выдумываются в UI. Восстановление backup должно повторно применять deletion/revocation tombstones. Публичная web-страница запроса удаления и store links — отдельный release gate, сейчас не реализованы этим документом.

Новый `Bridge::assertUserActive()` проверяет ACTIVE и явно выбранный UF_DELETE_ACCOUNT_BY_USER; отсутствие поля закрывает экспорт с BITRIX_SCHEMA_MISSING. Это защита чтения, не реализация уничтожения данных. Полный путь требует проверки на реальном Bitrix staging.

## Приёмка и владельцы

| Пакет | Владелец исполнения | Проверяемый результат |
|---|---|---|
| Оператор/цели/договоры/страны/retention | Владелец бизнеса + профильный юрист + infrastructure | Закрыты UNKNOWN/OPEN в data-map/register; указан источник и дата каждого решения |
| Consent ledger | Backend + mobile | Нет prechecked marketing; stale document/version, offline, duplicate и revoke проверены; без server receipt UI не пишет «сохранено» |
| Privacy network audit | Security + native QA | На чистом iOS/Android устройстве guest/login/deny/allow/logout; все endpoints/SDK совпадают с реестром; токены/формы отсутствуют в отчётах |
| Deletion | Backend + владельцы Bitrix/CRM/1С + QA | До/после проверены все хранилища/доступы; повтор/retry не восстанавливает пользователя; отдельно retention archive |
| Файлы | Backend + security | Свои вложения доступны, чужие запрещены; MIME/path traversal/oversize проверены; документация очистки временных файлов |
| Store declarations | Release owner + privacy | Декларации соответствуют фактической подписанной сборке, а не только package.json |

Текущее закрытое значение `liveWrites:false` в app-config не является доказательством соблюдения закона; оно удерживает непроверенные операции до реализации перечисленных gates. В release config `faceIDPermission:false`; наличие SecureStore не означает внедрённой биометрической авторизации. EAS non-preview hook запрещает неподготовленную store-сборку.
