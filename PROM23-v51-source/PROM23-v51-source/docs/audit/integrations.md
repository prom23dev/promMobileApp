## Контракты, которые нельзя потерять при переносе

- Заказ создаётся один раз в существующей бизнес-системе. `OnSaleOrderSaved` уже создаёт CRM deal по person type/branch; mobile не должен повторять этот side effect.
- B2C и B2B **равнозначно важны** по последнему уточнению пользователя. Consumer default снимает обязательность организации, но не скрывает закупку/спецификацию/коммерческое предложение.
- ProcurementRequest — отдельная заявка, source supplier upload лишь возможный технический reference. Нельзя смешать направление «стать поставщиком» с покупательской потребностью.
- Для всех write commands: authenticated actor, owned resource/organization, serviceRegion/settlement context, durable idempotency, согласия с версиями, минимальные CRM fields и проверяемый reference.
- Mobile BFF не вызывает HTML popups как API и не доверяет переданной цене/остатку/скидке/PAID. Backend failure — честная ошибка/pending, не локальный успешный заказ.
- Static registry consents ещё не durable consent evidence. History/analytics не должны получать raw комментарий, ФИО, email, телефон, ИНН или полный адрес.

## Что подтверждено и что оставлено программистам

Подтверждены классы, event wiring, source field mappings и наличие16 integration boundaries в таблице. Это не16 подключённых провайдеров: строки включают внутреннюю Sale-систему, adapters и import boundary. Проверка live auth, merchant/carrier capabilities, delivery tariffs, оплаты/отмены/refund, CRM acceptance/reference, 1С document retrieval и PD retention выполняется при последующем подключении. Никаких реальных операций этот аудит не делает и никаких дополнительных доступов сейчас не требует.
