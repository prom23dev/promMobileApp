# Web ↔ mobile parity

**Последнее уточнение пользователя: B2C и B2B равнозначно важны.** Consumer default не означает снижение B2B-приоритета. Личная покупка доступна без организации; закупка с файлом и корпоративные возможности заметны рядом, с самостоятельным сценарием.

Дата: 11.09.2026. MASTER4. Только чтение исходников и публичных страниц; PHP/Bitrix, формы, OTP, CRM и платежи не выполнялись. Реальные операции проверят программисты после подключения; staging и учётные записи не являются условием этой итерации. Статус BACKEND GAP означает неподключённый контракт, а не запрос доступа пользователю. Секретные значения не включены.

Функциональный паритет не означает одинаковую раскладку. Ни один generic workspace не считается выполненной синхронизацией. LOCAL/SNAPSHOT — рабочий локальный сценарий или импортированный контент, а не реальная учётная запись сайта.

## Главные восстановления по MASTER4

### B2C

- Default consumer flow сохранить, не требовать компанию. Реальная авторизация нужна поверх существующего User/OTP; форма входа без adapter не создаёт session.
- Заказы/повтор, избранное, comparison, WaitingList, отзывы/вопросы, обращения, возвраты, адреса, способы оплаты, уведомления/просмотренное уже существуют в source. Перенос — synchronization + права + states, не выдуманные записи.
- Сырой сбор карты из legacy source не переносить. Показ provider binding как зависимого шага — намеренное безопасное отличие.
- Account deletion source ставит флаг; нельзя обещать выполненное удаление истории/PD.

### B2B

- User ↔ несколько организаций ↔ персональная/организационная корзина. Текущий `organization-demo` — placeholder контекста, не доказанный company ID.
- Business rich content не потерян в backend: UF_* CMS selections и живые USP/FAQ. Mobile InformationScreen требует rich presentation, а не повторной генерации обещаний.
- Документы 1С имеют backend, даже если часть навигации скрыта. Счёт/УПД доступны после существующих условий; документы и ЭДО не приписывать каждой покупке.

### Закупка

Новый primary `/procurement` в текущем mobile route inventory **MISSING**. `quote` — alias business-advice и требует email/company/comment, но не умеет procurement file/ИНН/settlement. `quick-order` сохранить отдельным вторичным входом. Не переименовывать supplier (это входящая заявка поставщика) в закупку.

## Проверенный контент для следующей UI-фазы

Живые `/business/` и `/vendor/` повторно прочитаны GET; текст, headings, формы сохранены в `docs/audit/public-rich-content.json`. Ранее проверенные media и кейсы: `docs/discovery/visual-audit.md`, `project-gallery-assets-v7.json`.

**Business:** коммерческое предложение по составу; подтверждённый остаток и резерв; заказная продукция/ТЗ; доставка с согласованием габаритов/разгрузки; безналичный счёт; НДС/закрывающие документы/ЭДО после подключения; категории основных работ; проекты; отзывы и FAQ. «12 000 м²» относится к Краснодарскому складу; «С 2008 года» — история компании. Резерв «до 5 календарных дней» в FAQ условный, зависит от подтверждения/категории/оплаты — не переносить как безусловный SLA. Налоговые цифры source хранить как цитируемый контент, не как расчётное правило приложения: authoritative tax возвращает backend. Условия закупочной документации/тендеров в FAQ подтверждены; actual tender processing не вызывать.

**Production:** публичные стадии/конструкторское бюро/склад материалов/цех/контроль качества/отгрузка, реальные фото, проекты, награды/сертификаты, консультационная форма. Публичная страница содержит отзывы с `[название компании]` — не публиковать как доказательство. Цифры производственной площади/оборудования брать только с точным владельцем факта; не присваивать складу роль цеха. Robot Ø42 не подтверждён просмотренным корпоративным фото: только обозначенная технологическая иллюстрация, если добавляется позже. Слоган V7 «От нашего цеха…» в production больше не использовать по MASTER4.

**Не придумывать:** сумму бонусов; распределённые по складам остатки; сроки доставки; рейтинги без даты; отзывы; владение сторонними брендами; успешно отправленную заявку без backend reference.

Отдельный список WaitingList в mobile WorkspaceScreen не найден; есть command `/forms/product-notify`, но command не заменяет список сохранённых ожиданий. `/user-agreement/` отображается через `/pages/personal-data` (source URL совпадает), а не несуществующий `/legal/terms`.
