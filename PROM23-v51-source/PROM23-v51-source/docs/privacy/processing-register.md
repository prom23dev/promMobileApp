# V7 — реестр целей обработки и решений владельца

Дата: 11.09.2026. Статус: **проект внутреннего реестра**, не утверждённая публичная политика и не поданное уведомление РКН. Наименование и реквизиты оператора должны быть согласованы: `docs/20-consent-source-audit.md` фиксирует разные ОГРН в исходных документах. Не выбирать юридическое лицо по догадке.

Применимость оснований ниже — инженерная гипотеза для проверки юристом по реальной модели. Наличие формы или удобство маркетинга не создаёт законного основания. Текст [152-ФЗ](https://mintrud.gov.ru/docs/laws/130) различает договор, обязанности закона и согласие; срок хранения зависит от цели и специальной обязанности, универсальный «храним всё 5 лет» здесь не устанавливается.

## Согласия: что менять и как доказывать

В `sourceConsents.separate()` политика и обработка уже разделены; значения изначально false. Но форма **advice** (`mobile/src/forms/siteForms.ts:169`) использует `sourceConsents.combined()` с одной галочкой на два документа. Удалить этот паттерн при V7 реализации. Отдельность согласия с 01.09.2025 подтверждают [опубликованный 156-ФЗ](https://publication.pravo.gov.ru/document/0001202506240021) и [Минюст](https://to19.minjust.gov.ru/ru/events/3561/). Простое копирование текста сайта не закрывает требование.

Ознакомление с политикой не называть универсальным разрешением на любую обработку. Где заказ обрабатывается на основании договора/закона, юрист определяет нужные уведомления и согласия; не привязывать покупку к маркетингу или необязательной аналитике. Рекламные сообщения оцениваются по [ст.18 38-ФЗ](https://government.ru/docs/all/98086/). Разрешение OS notifications не является рекламным opt-in. Общая фраза в документе о cookies/всех партнёрах/иностранных странах не заменяет выбор и реестр получателей.

Проект consent event (реализовать сервером, сейчас отсутствует): `eventId`, внутренний `subjectId` либо доказуемый guest binding, `purposeId`, `channel`, `action:grant|revoke`, `documentId`, `documentVersion`, хеш неизменяемого текста, server timestamp, `formId`, app version/locale, request ID. События дописываются, а не перезаписываются одним boolean. IP/UA включать в доказательства только при обоснованной необходимости и сроке; не хранить OTP или текст формы внутри события. Backend проверяет актуальность документа, требуемые цели и права, записывает доказательство атомарно с операцией. Не принимает клиентское время/роль за истину.

Отзыв: отдельные настройки целей/каналов, понятный результат, прекращение новых заданий и отмена маркетинговой очереди, синхронизация sender/CRM, минимальное доказательство отзыва. Отказ от маркетинга не отменяет действующий заказ и обязательные сообщения по нему.

## Удаление аккаунта и запросы субъекта

Проект процесса: Account → «Удалить аккаунт» → объяснение последствий/сохраняемых категорий → необходимая проверка личности → серверный request ID → отзыв всех сессий и токенов → задания Bitrix/CRM/1С/рассылки/файлы → статус завершения. Публичный веб-путь работает без установки приложения. Удаление сессии из SQLite не является этим процессом. [Apple deletion](https://developer.apple.com/support/offering-account-deletion-in-your-app/), [Google deletion](https://support.google.com/googleplay/android-developer/answer/13327111?hl=en).

Законный архив чеков/договоров не уничтожается механически по кнопке. Для каждой сохраняемой категории назвать основание, срок, ограничить доступ и исключить повторное маркетинговое использование. Обработчики подтверждают выполнение; backup истекает по политике, а восстановление учитывает tombstone удаления. Не обещать «все данные мгновенно удалены», если это не соответствует процессу. Удаление личного аккаунта работника не должно уничтожать собственность организации; членство/права прекращаются, корпоративный архив обрабатывается по своему основанию.

Запросы доступа/исправления/прекращения обработки регистрируются, сроки рассчитываются по применимой статье 152-ФЗ и обстоятельствам. Точные регламентные сроки и ответственный контакт утверждаются владельцем до подключения. Для инцидентов подготовить обнаружение, ограничение доступа, оценку категорий/масштаба, сохранение доказательств и процедуру уведомления РКН по действующей ст.21; таймеры/формы проверяет ответственный по ПД, они не заменяются общим «ответим в течение месяца».

## Недостающие решения владельца — один пакет, без доступа к секретам

1. Единственный оператор/продавец или перечень лиц по сценариям, реквизиты, privacy contact и уполномоченный ответственный.
2. Где физически находятся main/replica/log/file/backup базы, кто имеет доступ; актуальность уведомлений РКН, перечень стран/получателей при трансграничной передаче.
3. Договоры/названия обработчиков: хостинг, Bitrix24 (облако или коробка), 1С, OTP, CRM, доставка, merchant/KKT/ОФД, Яндекс, сообщения, analytics. Секретные ключи в этот реестр не включаются.
4. Таблица retention по P-01…P-12, правовая причина каждого архива, удаление у подрядчиков, согласованные тексты и версии.
5. Ответственные и проверенный процесс жалоб/удаления/инцидентов. До их подтверждения соответствующие внешние потоки остаются выключенными.
