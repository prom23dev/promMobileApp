ТЕХНИЧЕСКОЕ ТЗ
по приведению prom23.ru и мобильного приложения в соответствие юридическому пакету 01.10.2026


Дата: 18 сентября 2026 года
Статус: обязательный checklist к production-релизу


1. Общий принцип


Юридические документы и фактическая работа сайта должны совпадать.


Нельзя считать задачу выполненной только после размещения новых страниц.


Проверяется вся цепочка:


PRODUCT
→ SELLER
→ CART
→ CHECKOUT
→ B2C OFFER / B2B CONTRACT
→ PAYMENT
→ RECEIPT / INVOICE
→ DELIVERY
→ RETURN / WARRANTY / CLAIM
→ ACCOUNT DOCUMENTS


2. Разделение B2C и B2B


2.1. В интерфейсе заказа должно быть явное состояние:


Для себя
Для бизнеса


2.2. B2C:
применяется публичная оферта /offer/


2.3. B2B:
применяется индивидуальный рамочный Договор поставки с собственным номером контрагента и документы конкретной сделки.


2.4. Не показывать B2B-пользователю текст:
«Нажимая кнопку, вы принимаете Публичную оферту для потребителей».


2.5. Не применять к B2B потребительские сроки возврата автоматически.


3. Seller architecture — P0


3.1. Для каждого заказа в backend обязательно поле:


seller_id


3.2. Для seller хранить:
legal_name
inn
kpp
ogrn
legal_address
contact_email
contact_phone
offer_url
invoice_details


3.3. B2C checkout до кнопки подтверждения показывает фактического продавца.


3.4. Вариант, минимизирующий риски:
все интернет-продажи B2C осуществляет ООО «Промышленник».


Если сохраняются региональные продавцы:
— каждый должен иметь собственные актуальные реквизиты;
— пользователь видит продавца до заказа;
— применимая оферта определяется seller_id;
— чек, возврат и претензия маршрутизируются к тому же seller_id.


3.5. Backend consistency check:


order.seller_id
payment.merchant_seller_id
fiscal_receipt.seller_inn
return.seller_id


должны совпадать.


При несовпадении — BLOCK ORDER.


4. Sale mode товара — P0


Добавить обязательное поле:


sale_mode:
BUYABLE
REQUEST_ONLY
CUSTOM_PRODUCTION


BUYABLE:
— фиксированная цена;
— определённый товар;
— доступное количество;
— checkout без обязательного звонка/согласования.


REQUEST_ONLY:
— «Уточнить цену» / «Получить предложение»;
— нельзя оплатить как обычный товар;
— форма запроса.


CUSTOM_PRODUCTION:
— «Заказать изготовление»;
— ТЗ/чертёж/файл;
— коммерческий расчёт;
— отдельное согласование.


Запрет:
BUYABLE + «Наличие уточните после заказа».


5. Остатки


Для BUYABLE использовать реальные состояния:


IN_STOCK
LIMITED
EXPECTED
OUT_OF_STOCK


LIMITED:
не разрешать заказать больше подтверждённого доступного количества.


OUT_OF_STOCK:
не показывать активную оплату.


REQUEST_ONLY:
не обещать наличие.


6. Карточка товара — P0


Для BUYABLE карточка должна содержать:
— название;
— артикул;
— основные характеристики;
— цена;
— единица продажи/комплектность;
— seller или доступ к seller-info;
— наличие;
— гарантия, если установлена;
— срок службы/годности, если применимо;
— способы получения;
— режим покупки;
— обязательные сведения о соответствии.


7. Сертификаты и декларации — P0


Если товар подлежит обязательному подтверждению соответствия, хранить:


compliance_type
document_number
registry_entry_url
status
valid_from
valid_to


На карточке:
«Сертификат/декларация»
→ прямая ссылка на запись в соответствующем реестре.


PDF можно прикладывать дополнительно, но не использовать вместо обязательной ссылки на реестр.


Если обязательное подтверждение не требуется:
показывать такую отметку только на основании проверенного товарного статуса.


8. Cart


Обязательная логика:
— checkbox у каждого товара;
— «Выбрать все»;
— сумма только по выбранным;
— checkout только выбранных;
— доставка считается по выбранным;
— невыбранные после заказа остаются.


Автотест:
3 позиции → выбрать 2 → order.items = 2 → третья остаётся в cart.

10. B2B checkout

— цену;
— НДС;
— способ получения;
— условия оплаты;

Текст:


«Заказ оформляется в рамках Договора поставки № [номер] и документов конкретной сделки». Если рамочный договор ещё не подписан, интерфейс должен показывать, что это B2B-заявка на согласование, а не завершённая поставочная сделка.


Показывать ссылку на PDF/электронную версию индивидуального Договора поставки в кабинете организации.


Сохранять:

13. Цена и payment methods — P0


Для одного SKU seller price не меняется из-за:
— карта;
— СБП;
— Яндекс Пэй;
— Сплит;
— цифровой рубль;
— оплата при получении.


Автотест:
same sku + same qty → item_price constant across payment_method.


Условия стороннего финансирования отображать отдельно.

18. Цифровой рубль — P0 legal gate


Юрист/бухгалтерия/финансы должны проверить:
1. Выручка ООО «Промышленник» за 2025 год.
2. Был ли на 01.01.2026 действующий договор о приёме электронных средств платежа с кредитной организацией, подпадающей под критерии Банка России.


Если оба условия выполнены:
включить цифровой рубль в B2C online payment flow.


Проверить:
— web;
— mobile app;
— чек;
— возврат.

45. Production release blockers


Нельзя выпускать production, если:
— seller не определён;
— old disclaimer остался;
— offer/contract не versioned;
— BUYABLE не имеет подтверждённой коммерческой логики;
— certificate links отсутствуют;
— payment price differs;
— extras preselected;
— remote return absent;
— claim channel absent;
— consent architecture объединена;
— consent-based tags fire before consent;
— digital ruble obligation применима, но не реализована;
— ЭПД required flow не готов;
— order seller != receipt seller.
