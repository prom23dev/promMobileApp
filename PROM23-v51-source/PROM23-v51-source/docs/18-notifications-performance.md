# Уведомления и производительность версии 0.3

## Что реализовано

Сервер формирует ленту из сохранённых тестовых заказов: создание и отмена имеют стабильный eventId. Повтор оформления не создаёт второй заказ/событие. Прочтение и настройки хранятся в SQLite по хешу сессии и контексту покупателя; чужое событие отклоняется, устаревший контекст возвращает 409. Удаление сессии удаляет связанное состояние.

Мобильная лента обновляется при фокусе и смене контекста. Ответ старого контекста не подменяет текущий. Из уведомления можно открыть соответствующий тестовый заказ. Проверка deep link разрешает только поддерживаемую внутреннюю цель собственного контекста; произвольные URL и пути отклоняются.

В исходном сайте обнаружены `UF_EMAIL_INFORM`, `UF_EMAIL_MARKETING`, `UF_SMS_INFORM`, `UF_SMS_MARKETING` и `Subscription::handleSubscription`. Локальная модель сохраняет отдельно сервисные и рекламные email/SMS/push-переключатели, все по умолчанию false. Она возвращает `consentRecorded:false`: это **тестовый черновик**, не синхронизация подписки и не запись юридически значимого согласия сайта.

В native-проект добавлен expo-notifications и обработчик открытия из системного уведомления. Он не запрашивает разрешение автоматически и не регистрирует токен устройства. Expo push relay не подключён. Устройства, APNs/FCM credentials и серверная отправка отсутствуют; доставки уведомлений в фоне ещё не было.

## Подключение к реальным событиям

Нужны проверенная мобильная авторизация и привязка устройства к пользователю; серверный журнал событий с eventId/orderId/context; идемпотентная отправка через согласованные провайдеры; отзыв токена после выхода/смены владельца; очистка недействительных токенов; отдельные настройки и доказательство согласия на рекламу.

Текущая таблица уведомлений сайта хранит HTML-сообщения без структурированных orderId/kind/eventId. Их нельзя надёжно получать парсингом произвольного HTML. Новый контракт событий должен сохранять существующие сообщения и типы событий. Отмена разрешения ОС, отказ/повтор доставки, открытие из завершённого приложения, чужой/отозванный заказ и смена организации проверяются на реальных iPhone/Android. Текущий валидатор UUID относится к тестовым ID; реальные Bitrix ID должны получить явное отображение в мобильный контракт.

## Измерения и ограничения

Стенд: 25 товаров, ответ каталога 85 687 байт. Выполнено 30 последовательных HTTP GET с этого Mac к серверу, без параллельной нагрузки: p50 **166,1 мс**, p95 **254,89 мс**, максимум **276,09 мс**. Полные измерения — `performance-v3-api.json`. Они включают сеть этого запуска и ничего не доказывают о скорости полного каталога или нативного экрана.

Используются виртуализированный список, порционная отрисовка, ограничения объёма ответов/времени ожидания и отмена устаревших запросов. Фото производства для главной уменьшено до 1000 px / 109 110 байт; тяжёлое видео на старте не загружается. Web JS около 3,4 МБ до транспортного сжатия, Hermes iOS около 4,8 МБ и Android 5,1 МБ. Размеры бандлов не равны времени запуска.

Цели из требований: p95 холодного запуска ≤2,5 с; открытие карточки ≤300 мс в согласованном сценарии; поиск ≤1 с; ≥95% кадров ≤16,7 мс на 60 Гц; API p95 ≤400 мс; ≥99,8% сессий без аварии в бете. Эти критерии **не приняты**: нужны полный ассортимент, pagination/cache, релизные сборки, фиксированные устройства/ОС/сеть, минимум 30 запусков на сценарий, серверная нагрузка и длительная бета. Сравнительных измерений WB/Ozon/ВсеИнструменты/Яндекс Маркета не выполнено.
