## Неизменяемые source-правила

- `site-source/local/class/Models/Organization.php:99` определяет членство по USER_IDS, с 24-часовым кешем. `organizations-add.php:97–117` при совпадении ИНН/КПП добавляет пользователя в этот список. **Это не подтверждённые полномочия представителя** и не основание дать доступ ко всем заказам компании.
- Переключатель source проверяет auth/sessid/членство до записи выбранной организации. В будущем BFF повторяет проверку прав каждой операции; client context и название роли недостаточны.
- `BasketUsers.php:88`, `:152` разделяет корзины user/org; `Regions.php:495` определяет тип цены, склад, способы оплаты/доставки. Эти данные берутся из реальной schema и provider, не из клиента.
- `Models/Order.php:69`, `:171` фильтрует владельца USER_ID. Новый bridge усиливает чтение свежим membership и owner+organization check. Не расширять этот доступ при переносе без утверждённой модели корпоративного доступа.
- Source order pipeline — `sale.order.ajax` → существующие events → Bitrix24; Documents1C отдельно получает PDF. Нельзя напрямую создать ещё одну сделку из BFF и назвать это тем же процессом. Подробности: [backend-audit](discovery/backend-audit.md).

## Целевая модель прав — требует утверждения, ещё не реализована

Backend должен различать user, organization, membership, verification и grants. Для membership нужны собственный ID, userId, organizationId, статус проверки, роли/разрешения, версия и время отзыва. ИНН/КПП служат идентификации организации, но не секретом и не доказательством права действовать от её имени.

| Роль из master | Зона, которую бизнес должен подтвердить | Что нельзя автоматически разрешать |
|---|---|---|
| Владелец | Подтверждение организации и делегирование в согласованных пределах | Самоназначение после ввода ИНН |
| Администратор | Управление участниками/адресами по матрице | Получение платёжных или финансовых полномочий только из названия роли |
| Закупщик | Черновик/заявка/корзина, возможно заказ в пределах лимита | Превышение лимитов или self-approval |
| Бухгалтер | Счета/документы/оплата в утверждённом scope | Изменение состава закупки и управление всеми участниками по умолчанию |
| Менеджер | Уточнить: сотрудник клиента или персональный менеджер продавца | Смешивание внутренних сотрудников продавца с членством клиента |
| Только просмотр | Явно разрешённые списки/документы | Изменения адресов, корзины компании, реквизитов или согласование |

Это перечень вопросов для permission matrix, а не выдуманные действующие grants. Запросы должны проверять subject + organization + resource ownership + permission + verification + актуальную версию контекста. Ошибка или отозванное членство закрывает доступ. Роль не берётся из feature flag; кеш revocation не может ждать сутки.

## Цены, документы и согласования

Текущий snapshot содержит **28 SKU / 10 popular / 23 oldPriceKopecks**. Прежняя цена — поле публичной карточки, не договорная скидка. `/api/v1/catalog` выдаёт stock=null, regionalPricing=false, checkoutEligible=false и одинаковые публичные данные для personal/organization. Главный каталог пока не потребляет эту пагинацию. На этом слое нельзя оформить B2B счёт или рассчитать кредитный лимит.

Для реального расчёта нужны: тип цены/договор/регион, SKU/единица/кратность/MOQ, доступность по складу, налоговые признаки, доставка, pay-system, персональные условия, действующая организация. Credit/deferred payment вводятся только если подтверждены бизнесом и учётной системой. Сервер выдаёт request-bound quote с версией корзины и TTL; изменившиеся цена/количество/права требуют повторного подтверждения.

Master предлагает draft → awaiting_approval → approved/rejected → invoice_created → awaiting_payment → paid → processing → shipped → delivered/cancelled. Сначала сопоставить эти состояния реальным Bitrix/1С статусам. Не переводить test-created в paid и не утверждать, что source уже поддерживает approvals. Для каждого transition определить исполнителя, permission, preconditions, журнал, idempotency и обратные события.

Счета/УПД, договоры, спецификации, акты, накладные, счета-фактуры, сертификаты и паспорта продукции имеют разное происхождение/доступ. Подготовленный Documents1C manifest подтверждает только ограниченную схему invoice/upd, а не весь список master. Файл выдают только после повторной проверки доступа; публичный постоянный URL для коммерческого документа не подходит.

## Три конкретных B2B сценария следующей реализации

| Сценарий | Серверный контракт / приёмка |
|---|---|
| Быстрый заказ SKU + quantity | V7 уже разбирает вставленные строки Excel/semicolon text и передаёт непотерянный список в форму КП через memory draft (30 мин, до 10 черновиков, текст≤2400 символов). Следующий этап — отдельный server preview/import result: found/unknown/ambiguous/unavailable, единицы/MOQ/кратность и текущая цена. Загрузка файлов CSV/XLSX ещё не реализована; нужны предел строк/размера, запрет формул/макросов/URL. Применение в корзину — отдельное подтверждение, атомарно и идемпотентно |
| Повтор заказа | Preflight текущих цен/остатков/удалённых SKU/кратности → показать изменения → подтвердить замену/добавление. Source `order-repeat.php:41` сначала очищает корзину; новый поток должен предотвращать её потерю при частичном сбое. Старые цены не передавать как authoritative |
| КП из товара/корзины | Context targets product/lines/quantity + действующая identity/org на сервере. Не просить вводить чужой orderId/userId. Получатель/номер обращения — только после server receipt; текущий `/forms/quote` не отправляет данные |

Персональный менеджер требует источника assignment в Bitrix/CRM, контактов, рабочего scope и разрешённого канала. Чат не имитируется формой, если такого канала нет. Вопрос из товара/корзины/заказа сохраняет context и не создаёт повторную CRM запись при retry.

## Handoff к команде

1. **Владелец B2B + юрист:** утверждают verification/grants/представительство, договорные условия, документы, лимиты и конфиденциальность.
2. **Bitrix/1С разработчик:** предоставляет schema/status/price/delivery/pay-system mapping, тестовых двух пользователей и двух организаций; никаких реальных секретов в документы/чат.
3. **Backend:** реализует identity/membership revocation, quote/order transaction, outbox и idempotency поверх существующих events.
4. **Mobile:** подключает реальные типизированные DTO, переводит view context из organization-demo в подтверждённую membership; не кастует snapshot stock=null в остаток 0/999.
5. **QA:** чужой пользователь/организация/документ, контекст другой вкладки, отзыв роли, изменение прайса, duplicate submit, offline/retry, сбой CRM/1С, возврат незавершённого заказа. Заявление о готовности требует настоящего staging заказа и документов, не только UI.
