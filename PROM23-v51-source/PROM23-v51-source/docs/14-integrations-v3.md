# Интеграции существующего магазина: Bitrix24, 1С, оплата и уведомления

Проверено по исходникам 11.09.2026. Реализация этой итерации — переносимый серверный **адаптер чтения**, конфигурация, диагностика и проверяемый контракт. Ядра/БД Bitrix в архиве нет. Рабочее соединение с магазином, доставка данных в Bitrix24/1С, платежи и push **не проверены и не заявляются настроенными**. Исходный PHP не исполнялся; реальные заказы, CRM-сделки, письма, SMS и платежи не создавались.

## Найденные блокеры записи

1. Первый обработчик `onSaleOrderSavedHandler($order)` использует `$order->isNew()`, тогда как второй обработчик того же D7-события принимает Event и читает ENTITY/IS_NEW. Совместимость первого нужно проверить на установленной версии Bitrix. После сохранения следует использовать семантику события IS_NEW; пропуск или повтор CRM-вызова недопустим.
2. В исходном CRM-транспорте явно выключены `CURLOPT_SSL_VERIFYPEER` и `CURLOPT_SSL_VERIFYHOST`. Перед включением реальной отправки требуется включить проверку сертификата/имени хоста, проверить HTTPS webhook и исключить ПД/секреты из URL и логов.
3. Бизнес-тип, организация и регион в событиях местами зависят от `$_SESSION`/`Regions`, а не только от сохранённого заказа. Нельзя запускать отложенный повтор под контекстом другого пользователя/организации. Нужна проверенная привязка мобильной авторизации к текущему контексту магазина.
4. Результат CRM-вызова нельзя считать подтверждённым на основании сохранения заказа. Нужны сохранение идентификатора/результата обмена и проверка повторов без второго `crm.deal.add`.
5. Конфигурация обмена заказами с 1С, реальные параметры платёжных систем, доставка, свойства/ENUM/HL и согласия находятся в отсутствующей БД/модулях. Наличие `Documents1C` подтверждает только механизм получения PDF.

## Что реализовано

Файлы сервера Node: `server/integrations/bitrix-client.mjs`, `readiness.mjs`, `cli.mjs`. Переносимый PHP-пакет: `integrations/bitrix/endpoint.php`, `src/Bridge.php`, `src/ReadOnlyBitrix.php`, `src/DocumentManifest.php`. Образец серверной конфигурации: `integrations/bitrix/config.env.example`.

PHP-адаптер использует существующие `Bitrix\Sale\Order::load`, `Prom\Model\Order::getOrderOrganizationId`, настройки `Prom\Documents1C::config` и ORM-таблицы документов/уведомлений. Он не вызывает `Order::save`, `Bitrix24Webhook::createDeal`, `Documents1C::agent/run`, платёжный компонент или отправку сообщений. Нет параметра, который включает запись.

У исходного `Documents1C::getOrderDocumentLink` есть побочный эффект: при отсутствующем HL-блоке `getEntityClass()` вызывает `log()` и записывает файл из LOG_FILE (`Documents1C.php:360–380`, `:596–607`). Поэтому новый `DocumentManifest` читает HL напрямую, сначала проверяет наличие блока и полей ID/UF_ORDER_ID/UF_TYPE/UF_LINK, затем выбирает только записи проверенного заказа. Отсутствующая схема возвращает `BITRIX_SCHEMA_MISSING`; исключение SDK — `BITRIX_READ_UNAVAILABLE` без SQL, пути и вызова исходного журнала. Сохраняется правило последней записи по типу: если новый файл отсутствует, старый не подставляется. Дополнительно разрешены только файлы внутри реального каталога upload; путь не выдаётся клиенту.

Readiness использует SELECT 1, чтение списка зарегистрированных обработчиков/агента и `Documents1C::config()`. В проверенной версии config только загружает массив настроек; перед вызовом проверяется доступность файла. Readiness не вызывает разрешение HL через исходный Documents1C, его журнал, агент или getter уведомлений с отметкой просмотра. Это ограничение касается бизнес-операций нового адаптера: защита от повтора намеренно создаёт nonce-файлы, а bootstrap, загрузка модулей и ORM установленного Bitrix могут менять служебные кеши. Поэтому отсутствие любых записей во всей чужой среде без её изоляции не заявляется.

| Operation | Результат | Ограничение |
|---|---|---|
| `readiness` | Наличие runtime/модулей, регистрация order saved handlers и агента документов, только признаки конфигурации CRM/1С | Не проверяет сеть 1С/CRM и не запускает агент |
| `order.export` | Номер/статус/тип покупателя/оплата как факт/сумма в копейках/товары/ARTICLE | Только собственный заказ указанного контекста; без контактов, адреса и платёжных реквизитов |
| `documents.manifest` | Доступные типы уже сохранённых документов | Только свой B2B-заказ; UF_LINK и скачивание не выдаются, `downloadEnabled:false` |
| `notifications.export` | Последние 10 записей конкретного контекста | Прямое чтение ORM, без отметки просмотра; HTML превращается в текст, неподтверждённый target/deep link — null |
| `preferences.export` | Реальные четыре email/SMS-флага | Никаких изменений подписки или кампаний; push помечен ненастроенным |
| Любая операция записи | HTTP 503 `BITRIX_WRITE_NOT_READY` | Не отправляется из Node и не выполняется PHP |

Каждый успешный ответ содержит `protocol:'prom23-bitrix-readonly-v1'`, `operation`, `writeEnabled:false`; персональный экспорт также возвращает проверенный `{userId, organizationId}`. Node проверяет этот контекст. Это отдельный серверный протокол; sandbox-токены и organization-demo **не преобразуются** в реальный userId/orgId. В мобильный HTTP API он пока не подключён, чтобы не создать обход реальной авторизации.

S2S-запрос — POST только на `/local/prom23-mobile/endpoint.php`, JSON до 32 КБ. Разрешённые операции и поля перечислены в Bridge::request. Для чтения заказа/документов тело `{operation, actor:{userId,organizationId}, orderId}`. Для уведомлений/настроек orderId отсутствует; для readiness actor не нужен.

HMAC-SHA256 подписывает `POST`, точный путь, timestamp, одноразовый nonce и SHA-256 тела, разделённые переводами строк. Допуск времени ±60 секунд. Секрет — файл с 64 hex-символами, права 0600, вне document root; nonce-каталог — 0700, тоже вне document root. Ключ не передаётся по HTTP. PHP отклоняет браузерные Origin/Cookie, повтор nonce и пользователей вне серверного pilot allowlist. Для B2B членство проверяется свежим запросом по схеме `Organization::checkUserInOrganization`, без её 24-часового кеша. Заказ дополнительно проверяется по USER_ID и ORGANIZATION_ID. Юрзаказ без корректного ORGANIZATION_ID отклоняется, а не превращается в личный.

Node требует явный HTTPS origin магазина и точный путь, проверяет TLS стандартным транспортом, не следует редиректам, ограничивает ответ 1 МиБ/5 сек. и не делает автоматических повторов. Публичные/внутренние CRM webhook не являются допустимыми URL. Сторонние error-message, URL и секреты не копируются в диагностику. Allowlist/ключ даёт доверие только серверному вызывающему компоненту; он обязан получать actor из проверенной авторизации, а не от клиента.

## Уведомления: точный контракт сайта для следующего мобильного шага

Источник: `local/class/Models/EO/UserNotifications.php`: таблица `b_prom_user_notifications`, поля ID, USER_ID, ORGANIZATION_ID, MESSAGE, SHOW_NOTIFICATION, CREATED_AT, UPDATED_AT. Модель хранит последние 10 записей пользователя/контекста, удаляет устаревшие через 30 дней. `getUserNotifications` сама помечает записи просмотренными; использовать её для фонового GET значило бы молча менять статус. Read-only bridge намеренно читает ORM напрямую.

В `OnOrderAdd`/`OnSaleStatusOrder` сообщения создаются HTML-строками с номером заказа. Структурированных orderId, kind, eventId, target/deepLink в таблице нет. Их нельзя достоверно восстановить парсингом произвольного текста. Для новых push понадобится отдельный структурированный журнал событий со ссылкой на заказ, идемпотентным eventId и проверкой текущего доступа при открытии.

`local/ajax/lk/notifications/notifications.php:23–36` сохраняет:

| Поле запроса сайта | Поле пользователя | Значение |
|---|---|---|
| email_order_info | UF_EMAIL_INFORM | Email о заказах |
| email_promotions | UF_EMAIL_MARKETING | Маркетинговый email |
| sms_order_info | UF_SMS_INFORM | SMS о заказах |
| sms_promotions | UF_SMS_MARKETING | Маркетинговые SMS |

Маркетинговые поля дополнительно передаются в `Subscription::handleSubscription`. Нельзя заменить этот вызов только локальным переключателем и назвать подписку синхронизированной. Изменение настроек требует исправления/проверки авторизации, CSRF, результата сохранения и отделения согласий. APNs/FCM, device tokens, platform permissions и настройки push в этих исходниках не обнаружены. Это новая инфраструктура для уже существующих типов событий, а не подтверждённая интеграция: нужны APNs/FCM тестовые credentials, app identifiers, настоящие устройства, тест доставки/отказа/отзыва/повтора/deep link. Ни одной реальной рассылки эта итерация не запускает.

## Что точно нужно для подключения и сохранения полного процесса

1. Изолированный экземпляр **самого магазина**: ядро и лицензия Bitrix, его БД/HL/ENUM/свойства, vendor и модули; read-only DB-учётка для экспортного пилота. Нельзя восстанавливать его поверх `zavod-antibpla.ru`.
2. Проверенные тестовые пользователи B2C и двух B2B-контекстов, актуальные членства и правила верификации представителя. Затем явная привязка мобильной авторизации; секрет S2S остаётся на сервере.
3. Установка PHP bridge в отдельный `/local/prom23-mobile/` только после просмотра init/агентов/событий этого staging. NO_AGENT_CHECK/статистические флаги заданы, но модифицированный bootstrap может содержать собственные побочные эффекты — нужен изолированный запуск/ограниченная DB-учётка. Серверные ключ/nonce-каталог и передача env в PHP-FPM вне публичного корня. Значения credentials не публикуются.
4. Readiness и негативные проверки: неверный ключ/nonce, чужой userId/orderId, другая организация, отозванное членство, неполный ORGANIZATION_ID, недоступный документ. GET не должен запускать CRM, агенты, оплату или отметку прочтения.
5. Для записи — реализовать серверный расчёт и создание через восстановленный checkout workflow, с теми же region/personType/warehouse/coupon/delivery/pay-system/property rules. Идемпотентность должна находиться в той же устойчивой БД и возвращать существующий orderId после неопределённого результата. Запрещено повторять прямую CRM-сделку из приложения или Node.
6. На контролируемом заказе подтвердить полный путь: сохранение Bitrix → события и ARTICLE/ORGANIZATION_ID → ровно одна сделка нужной воронки/филиала → существующий канал обмена заказами 1С → появление проведённых документов → получение агентом → доступ владельцу. Отдельно проверить отказ CRM/1С и безопасный повтор без дублей. До этого флаги `*Tested` остаются false.
7. Платёжный sandbox и callback/deep link проверяются отдельно через существующий модуль, включая Яндекс Пэй/Сплит в фактической конфигурации, если они настроены. Статус PAID нельзя выставлять мобильным запросом. Платёжные/кассовые реквизиты не принимаются этим адаптером.

Read-only адаптер можно перенести и проверить уже сейчас на подходящем staging. Полный order/payment bridge намеренно не выдаёт успешный ответ без недостающего ядра, бизнес-конфигурации и сквозных тестов.
