## Что уже безопаснее в исходнике

local/php_interface/include/secrets.php:121–131 централизует Yandex/DaData/Bitrix24/SMS/CDEK/export secrets через prom_env. Поэтому нельзя утверждать, что все интеграции содержат hardcoded fallback. Но отдельные legacy handlers и JS всё ещё обходят эту схему. В mobile/BFF следует переиспользовать эту границу, не переносить ключи из архива в environment приложения.

## Выполненная проверка и защита передачи

scripts/secret-scan.py выводит только location/type/status, держит найденные значения в памяти и проверяет их отсутствие в коде нового приложения, web export и исходных ZIP. При обнаружении переноса в эти артефакты возвращает exit 1. Встраивается перед упаковкой. Это узкий контролируемый guard от переноса известных literals, не универсальный детектор всех возможных секретов. Итоговый machine report: secrets-audit-v8.json.

В переданном дереве и текущем проекте нет .git. Поэтому git history не исследована, прежнее удаление или отзыв ключей не подтверждаются. Историю должен проверить владелец исходного репозитория; ключи, попавшие в историю, считаются требующими замены.

## Что не выполнено и почему

Ключи не перевыпущены и не отозваны: нет подтверждённого доступа к кабинетам владельцев интеграций, а изменения могут остановить действующие сайты. Пользователь уточнил, что на этом этапе достаточно анализа присланного кода; реальные подключения проверят программисты. Исходный архив не отправляется в source ZIP и не размещается на сервере. Новый location adapter использует только отдельную серверную конфигурацию; при отсутствии секрета провайдер закрыт. Никаких real-looking fallback values.

Порядок владельцу: определить сервис/сайт/окружение → выпустить новый ключ с минимальными scopes → установить серверный env → проверить разрешённую staging-операцию → отозвать старый → проверить ограничения и журнал → повторно проверить исходники, историю и артефакты. Знание старого ключа не даёт mobile-клиенту полномочий на его использование.
