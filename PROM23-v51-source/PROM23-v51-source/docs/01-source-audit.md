## 3. Авторизация и интерфейсы

Текущий пользовательский поток — браузерная сессия Bitrix. Обработчики форм проверяют `check_bitrix_sessid()`, затем сервер обращается к собственному REST через `Prom\\Lib\\Rest`. Адрес REST собирается из серверных констант `REST_APP_ID_AUTH` и `REST_KEY_AUTH` (`local/class/Lib/Rest.php:11`): такой webhook-ключ нельзя помещать в iOS/Android-приложение.

Кастомный REST регистрирует регистрацию по email/телефону, вход по email/телефону и восстановление пароля (`local/class/Rest/RestAuthController.php:36`). Результат содержит `user_id` и `authorize`, но здесь нет контракта выпуска, ротации и отзыва мобильных access/refresh token (`local/class/Rest/RestAuthController.php:297`). `local/rest/index.php:1` — административный интерфейс управления Bitrix webhook, а не публичный consumer API.

OTP содержит TTL 10 минут, лимиты выдачи/проверки по идентификатору, IP и сессии, случайный шестизначный код и ограничение трех попыток на запись (`local/class/Models/ConfirmationCodes.php:14`, `:33`, `:143`). Это положительные элементы, которые нужно сохранить. Атомарность одноразового погашения при конкурирующих запросах не подтверждена: используется read-modify-save (`:159`).

Список заказов и детали фильтруются по текущему `USER_ID` и выбранной организации (`local/class/Models/Order.php:31`, `:689`). Следовательно, действующая семантика — собственные заказы пользователя в контексте компании; общий просмотр заказов всех сотрудников не доказан. Это нужно согласовать отдельно до проектирования ролей организации.

## 5. Блокеры, которые нельзя переносить в мобильный API

Приоритет P0 означает «закрыть до подключения реальных данных/платежей», P1 — «закрыть до выпуска». Это подтвержденные особенности кода и зоны недоказанной безопасности; эксплуатация уязвимостей не проводилась.

### P0. Присоединение к существующей организации по публичным реквизитам

`local/ajax/lk/organization/organizations-add.php:24` принимает ИНН/КПП; `:99`–`:117` при найденной организации добавляет текущего авторизованного пользователя в `USER_IDS` без приглашения/одобрения. Переключатель затем проверяет только membership (`local/ajax/lk/organization/action-organizations-switcher.php:18`). Чтение данных организации проверяет `USER_IDS` (`local/class/Models/Organization.php:192`).

Отдельная верификация существует и имеет срок действия (`local/class/Models/Organization.php:277`), но найденные вызовы `isUserVerified` используются в header/menu, где выводится предупреждение «Скоро без верификации…» (`local/templates/main/components/bitrix/menu/organization/template.php:31`). В исследованных операциях не найден единый серверный запрет для неверифицированного участника. Поэтому знание ИНН нельзя считать доказательством полномочий. Нельзя утверждать, что это открывает все чужие заказы: `Order` отдельно ограничивает их `USER_ID`.

Исправление: отдельные состояния «найдена / запрос доступа / одобрена», роли и права, проверка membership + полномочий на каждой B2B-операции; безопасное приглашение/ручная верификация. Не изменять реальную членскую запись при простом поиске ИНН. При отзыве доступа немедленно инвалидировать права; текущий TTL кэша membership — 24 часа (`local/class/Models/Organization.php:110`).

### P0. «Привязка карты» является незавершенным путем обработки карточных данных

`local/ajax/lk/payment-methods/add-card-action.php:24`–`:42` принимает номер, срок и CVV из `$_REQUEST`, задает банк/тип карты константными заглушками и вызывает локальное сохранение. `local/class/Models/ConfirmedCards.php:141`–`:151` сохраняет переданный `CARD_NUMBER`; в этой ветке нет маскирования/токенизации. Сохранение CVV данным методом не обнаружено — не следует утверждать обратное.

Нельзя подключать этот endpoint к мобильной форме реальных карт. Нужен SDK/hosted payment flow подтвержденного платежного провайдера, сохранение только токена и разрешенных маскированных реквизитов. Состояние оплаты подтверждает серверный callback с проверкой подписи и сверкой заказа/суммы, а не redirect клиента. Наличие безопасного готового callback в отсутствующем платежном модуле проверить невозможно.

### P0. Документы заказов записываются в публичный каталог

`local/php_interface/lib/Documents1C.php:226`–`:242` формирует постоянную ссылку и записывает PDF под document root; `:228` прямо указывает, что `/upload` открыт наружу. Непредсказуемый суффикс снижает угадывание, но не проверяет право получателя и не отзывает уже переданную ссылку. Фильтр списка по `USER_ID` (`:412`) не защищает прямую загрузку файла.

Нужно закрытое файловое хранилище и авторизованный download endpoint либо короткоживущая подписанная ссылка с проверкой прав при выдаче. Реальную настройку nginx/Apache надо подтвердить: она отсутствует, поэтому общедоступность на живом сервере не тестировалась.

### P1. Удаление аккаунта не реализует удаление связанных персональных данных

`local/class/Models/User.php:203`–`:217` только устанавливает `UF_DELETE_ACCOUNT_BY_USER=true`, не проверяет результат `CUser::Update` и всегда возвращает `true`. `local/templates/main/header.php:264`–`:272` запускает это GET-параметром и завершает сессии. UI при этом обещает потерю истории, карт, компаний и документов (`local/ajax/lk/info/edit/delete-account.php:18`). Во всем PHP-коде не найден обработчик очистки/анонимизации по этому флагу.

Нужен подтверждаемый POST-запрос удаления, повторная проверка личности для чувствительной операции, отзыв сессий/токенов и job удаления/анонимизации связанных данных с контролем результата. Данные, которые требуется хранить по применимому закону, следует отделять, ограничивать и честно описать срок/основание хранения; срок нельзя придумать из исходников. Требования App Store/Google Play и правовую модель необходимо проверить в отдельной compliance-работе.

### P1. Отзыв сессии может сообщать ложный успех

Положительное: `local/ajax/lk/info/edit/terminate-session.php:16` проверяет авторизацию и CSRF; модель фильтрует сессии по текущему пользователю (`local/class/Models/User.php:298`). Но исключение возвращает `status=true` (`:334`–`:338`), а при ненайденном ID также выполняется общий success (`:328`). Удаление другой сессии зависит от конкретной таблицы `UserSessionTable` (`:322`), конфигурация используемого backend сессий неизвестна. `getActiveSessions()` возвращает сырой `SESSION_ID` (`:251`) — такой идентификатор нельзя включать в мобильный DTO; отдавать отдельный opaque ID устройства.

Исправление: проверяемый отзыв в фактическом хранилище и remember-me механизме, корректные ошибки, endpoint отзыва всех устройств, мобильные токены с ротацией. Тест должен доказать, что ранее действовавшая сессия после отзыва больше не авторизует запрос.

### P1. Контекст компании/корзины хранится в общей сессии

`local/class/Models/Organization.php:19`, `local/templates/main/header.php:114`–`:135`, `:173`–`:193` переключают организацию и корзину через `$_SESSION`. Мобильный клиент с параллельными запросами, deep links и повторными попытками не должен зависеть от того, какой HTML-экран последним изменил сессию. Кроме того, «Повторить заказ» очищает текущую корзину до наполнения (`local/ajax/lk/orders/order-repeat.php:40`–`:53`), без транзакционного preview/merge.

API должен принимать явный `customerContext`, проверять его на каждой операции, версионировать корзину и пересчитывать цены сервером. Для оформления/оплаты/возвратов — идемпотентность и защита от двойного нажатия/повторной доставки. Повтор заказа должен показывать изменения цен/наличия и явно согласованно работать с текущей корзиной.

### P1. TLS в тестовом REST-потоке может отключаться

`local/class/Lib/Rest.php:260`–`:284`: для `APP_TEST=Y` проверка TLS по умолчанию отключена, причем через этот запрос идут пароль/OTP. Мобильный API и используемый им серверный канал должны проверять сертификат и имя хоста также в staging. Не встраивать в сборку исключения доверия и серверные webhook-ключи.

### P1. Существующий web API не равен готовому API для магазинов

В приложении потребуются версия контрактов, стабильные ошибки, pagination, timeout/retry policy, request ID, лимиты, аудит доступа, обработка персональных данных, отзыв токенов и договорные тесты. Отдельный роутер в `local/route.php:10` содержит только `GET /local/api/delivery/points`; он не покрывает покупки. Штатные Bitrix CSRF-проверки нужно сохранить для браузера, а мобильную схему auth спроектировать отдельно, не отключая проверки ради совместимости.

## 7. Критерий готовности интеграции

Сначала воспроизводимый staging и согласованные контракты. Затем устранение P0, проверка сценариев B2C/B2B на тестовых данных и платежном sandbox. Полноту переносимых функций проверять по `02-feature-parity.md`. Никакие показатели «как WB/Ozon» не доказаны статическим аудитом: необходимы профилирование release-сборок на устройствах, нагрузочное тестирование API и измерение пользовательских сценариев.
