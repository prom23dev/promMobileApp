# Передача интеграций программистам — MASTER5

Код достаточен для подготовленного интерфейса, официального справочника и безопасных контрактов. Реальные аккаунты, остатки, цены по складу, заказы, платежи, CRM и1С ещё не подключены. Не включайте эти возможности заменой флага: сначала реализуйте и проверьте соответствующий адаптер.

## Что уже вызывается

- Public snapshot BFF: app-config/home/catalog и официальный location search/detail.
- `GET /api/v1/content/pages/:slug`:17страниц, plain text/stable IDs, ETag/304, CORS и fallback. [Контракт](../docs/api/public-content.md).
- `GET /api/v1/products/:productId/details`:28карточек,144image references/136уникальных реальныхфайлов720, описание/преимущества/комплектация и source visibility форм. [Контракт](../docs/api/product-details.md).
- `GET /api/v1/products/:productId/availability`: требуется локальная session и выбранный официальный settlement. Ответ связан с productId/settlementId/locationVersion/buyerContext; без Bitrix mapping статусunknown, количествоnull. Это не боевой остаток.
- Локальные корзина, избранное, сравнение, просмотренное, поиск и выбор settlement. Sandbox token не авторизует на сайте.
- Server-only read-only Bitrix bridge для readiness/order export/document manifest/notifications/preferences. Он выключен без явного серверного конфига. Его PHP policy tests не заменяют тест с настоящими core/DB.

## Последовательность подключения

1. **Окружение и actor.** Поднимите BFF рядом с существующим Bitrix в отдельном согласованном окружении. Изучите `bitrix/endpoint.php`, `bitrix/src/Bridge.php`, `ReadOnlyBitrix.php`, `server/integrations/bitrix-client.mjs`. HMAC key и site credentials только на сервере. Не используйте найденные в архиве ключи и сторонний webhook. Чтение защищённых данных разрешайте только проверенному пользователю и его организации; revoked/deleted actor отклоняйте. Production auth/refresh/OTP пока отсутствует в мобильном transport.
2. **География и коммерческий контекст.** ПолныйГАР уже содержит160478актуальных объектов96регионов. Он не определяет склад/прайс. Реализуйте `resolveCommerceContext` для официального settlement и проверенного buyer/organization actor; верните существующие ServiceRegion/Store IDs и versioned contextKey. Исправление source B2C DEFAULT_CITY override сохраняется. Адрес доставки и филиал остаются отдельными сущностями.
3. **Наличие и цены.** Подключите `readInventory` к StoreProductTable с подтверждённой полной областью складов и явными нулевыми строками. Не используйте Helpers::getStoreQuantity как полную матрицу: он фильтрует AMOUNT>0. CatalogProvider находится в `site-source/local/php_interface/lib/Basket.php:188`, типы цен — CATALOG_GROUP_XML_ID/Regions/BasketUsers. Не рассчитывайте реальные цены или резерв из публичного снимка. Выполните cart revalidation после изменения settlement, склада, организации, количества, цен и акций.
4. **Формы и файлы.** Замените `loadSiteFormContext`/`submitSiteForm` source-compatible BFF-сервисами. Внутренний registry formId должен отображаться на whitelist CForm/handler, а поля/required/answer IDs/enums — на реальную БД. Не передавайте arbitrary WEB_FORM_ID или цену из UI как authority. Для возврата нужны завершённый принадлежащий актору заказ, выбранные товары и REASONS; для обращения THEME/TAGS_HELP; для ЭДО operators; для экскурсии доступные даты. Организационные файлы и user media требуют подтверждённых upload IDs, допустимых MIME/размеров/числа, проверки содержимого и правил хранения. Реальный reference только после сохранения.
5. **Согласия.** Передавайте отдельные непредвыбранные решения с версиями документов и фиксируйте принятие сервером, временем и целями. Публичный content API не меняет canonical consent versions и не выдаёт checkbox за сохранённое согласие. Транзакционные и маркетинговые каналы независимы; отсутствие настройки не означает согласие. Настоящие APNs/FCM пока не подключены.
6. **Заказ, CRM и1С.** Создавайте заказ единожды через существующую Bitrix Sale-систему и её события. `events.php:221–371` уже вызывает существующий Bitrix24 deal flow; не создавайте второй прямой lead/deal параллельно. Идемпотентность и повторное подтверждение quote должны защищаться на сервере. `Documents1C` экспортирует документы по своим условиям; наличие класса не доказывает полный обмен заказами. Invoice/УПД и паспорт конкретного товара — разные manifest. Проверяйте владельца/организацию/покупку перед выдачей ссылок.
7. **Оплата и доставка.** Используйте реальные account-configured provider offers, связанные с заказом/суммой/контекстом/expiry. В source ProductDeliveryCalculator активны YandexDelivery/CdekCourier/Pickup; один найденный Dellin class не означает подключённый вариант. Не копируйте hardcoded сроки/адреса, debug payload или нулевые fallback-габариты. Pay widget не гарантирует Сплит/Плюс. PAN/CVV не собирать собственными полями; provider session и проверенный backend payment status обязательны. Redirect/callback не означает PAID/refund.
8. **Публикации.** `loadProductPublications` подключён к реальным `HLBL_ID_REVIEWS`/`HLBL_ID_QUESTIONS` через `WorkspaceDriver::publications()` (`r-sort/r-rating/r-with-photo/r-with-replies` — client-side имена; source-фильтры `UF_ACTIVE`, `UF_SKIP_RATE` (только отзывы, только публичный список — не личный кабинет), `UF_TARGET_ID`/product scope и владелец reply/edit/delete сохранены). Курсорная пагинация (`cursor`/`nextCursor`, страница20, bounded2000) реализована этап8 вместо прежнего `truncated`-среза; см. `docs/parity/runtime-forms.md`. Реальные отзывы, ответы, файлы и success не имитируются. Комментарии статей в source отключены и вUI не добавляются. Выборочное удаление старых фото при `review-edit` — новая возможность этого driver'а (у source её нет вообще), подключена целиком включая мобильный UI (`FormScreen.tsx`).
9. **CMS.**17страниц обслуживаются curated snapshot. `scripts/export-public-content.py` обновляет его из проверенного sitePages JSON literal, не исполняя архив. Реальный CMS adapter должен сохранить page/section IDs, provenance/revision, проверку текста/ссылок. `editorialContent.ts`/branch data пока отдельный локальный слой, не управляемый этим CMS endpoint.

## Адрес API на устройстве

В preview HTTP разрешён только для согласованного локального транспорта. `mobile/src/api/local.ts` без настройки использует `/api` для web и `http://127.0.0.1:8090/api` для native. На телефоне127.0.0.1 — сам телефон, не Mac или удалённый BFF. Для настоящей сборки задайте публичный HTTPS BFF URL через `EXPO_PUBLIC_LOCAL_API_URL`; для content/home можно также согласованно задать `EXPO_PUBLIC_APP_API_URL`. Эти PUBLIC переменные не должны содержать ключи/пароли. Не публикуйте бинарник с loopback fallback, тестовым transport или неподключённой авторизацией. Сборка/подпись/приёмка магазинов ещё не выполнены.

## Проверки перед включением реальных функций

Локально уже проверены schema/provenance, ETag/CORS, unknown≠zero, отсутствие опасных URL/приватных документов в публичном DTO, session/location/buyer binding, malformed optional snapshot, timeout/fallback, official location/CAS и legacy write gates. Итоговые логи находятся в `docs/testing/`; матрицы — `docs/audit/function-parity.md`, `forms-parity.md`, `backend-master5-clauses.json`.

После подключения нужны настоящие проверки: один пользователь/две организации/чужой пользователь/отозванный actor; location/warehouse/price change; повтор запроса и истёкший quote; provider errors; одно создание заказа иCRM event; платёж/отмена/возврат; owner-scoped documents; загрузка/модерация media; согласия и фактическое отключение рассылок. До их выполнения соответствующий статус остаётся RUNTIME BLOCKED. UI click-through, native device matrix, stores и юридическая проверка имеют отдельные критерии, их не закрывают серверные unit tests.
